# Known issues — XR32 DAY+NIGHT test build, trunk r12377 (testing-3)

testing-3 changes only how the finished 32-bit picture reaches the window: it uploads the changed parts of the screen
instead of the whole screen, draws the screen texture without blending, and marks as changed what the 16-bit renderer
marks. What the renderer draws is unchanged from testing-2. Part A lists what is still open, Part B what testing-3
changed, Part C the defects of official trunk r12377 itself. The numbering of testing-1 and testing-2 is kept.

Every result below was measured on this build's executables, with a control that shows the check can fail, unless it
says otherwise. The full certification is `reports/XR32-DIRTY-REGIONS-CERTIFICATION-01.md`.

## A. Still open in this test build

### T1. After a live theme change two small toolbar elements can keep their old picture (trunk behaviour)

When the theme is changed while the game runs, two small parts of the screen can keep their old picture until
something else redraws them: the compass at the top right (768 px at 1920×1080) and a small element at the left of
the toolbar (82 px). The game draws the compass without marking it as changed (`gui/simwin.cc`,
`display_img_aligned(..., false)`), so a renderer that sends only the changed parts does not send it. The official
16-bit renderer of r12377 leaves exactly the same pixels stale in the same test (compared pixel by pixel, 16 runs).
testing-2 did not show it only because it sent the whole screen every frame. Not caused by XR32; not changed here,
because the fix belongs in trunk.

### A4. Coast water tiles have no 32-bit detail

Unchanged from testing-2. The water tiles on sloped coasts are generated by the game from the 16-bit water images, so
they stay 16-bit. Open: a new graphics feature that needs a design decision.

### A7. Night pictures cost memory

Unchanged from testing-2 (by design): an object with a night picture keeps a second full-size 32-bit picture.
testing-3 keeps no new memory: the map of changed screen tiles already existed in testing-2, and the upload walk only
uses a temporary of one tile row while it runs.

### A8. The pak syntax is a prototype

Unchanged from testing-2 (by design). The makeobj of this release is testing-2's, byte for byte.

### A9. Builds and platforms

Unchanged from testing-2, plus what testing-3 measured:

- **Where Linux was tested:** Debian 13 under WSL 2 on Windows 11, SDL's dummy video driver and the WSLg session
  (X11 through XWayland, and Wayland). **WSLg is not a native Linux desktop**: a native X11 or Wayland desktop, HiDPI
  above scale 1, more than one display and GPU drivers other than WSLg's were not tested.
- Windows was tested on one display (3440×1440) with the GPU's Direct3D renderer that SDL picks by default.
- Not tested: macOS, Android, ARM.

### A10. A zoom change costs about 1 ms more

Unchanged from testing-2 (the first frame after each zoom change, exact 16-bit sampling).

### N2. Identical 16-bit images are merged only within one pak file

Unchanged from testing-2. Open.

### N3. A double-size (MRES) split of a shared image may lose its 32-bit data

Unchanged from testing-2. Found by reading the code; not reproduced. Open.

### N4. Memory released only at exit

Unchanged from testing-2. Open, no visible effect.
