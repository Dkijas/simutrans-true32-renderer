# Known issues — XR32 DAY+NIGHT test build, trunk r12377 (testing-2)

testing-2 is a consolidation of testing-1 on the same trunk, r12377: it fixes five defects of the 32-bit renderer and
adds no graphics feature. Part A lists what is still open in this test build, Part B what testing-2 fixed or could not
reproduce, Part C the defects of official trunk r12377 itself (unchanged from testing-1: they affect both programs of
every package and are not caused by XR32). The numbering of testing-1 (`docs/KNOWN-ISSUES-r12377.md`) is kept.

Every result below was measured on this build's executables, each with a control that shows the check can fail
(testing-1 or XR32 off), unless it says otherwise. The full certification is `reports/XR32-CONSOLIDATION-01.md`.

## A. Still open in this test build

### A4. Coast water tiles have no 32-bit detail

The water tiles on sloped coasts are generated by the game itself from the 16-bit water images, so they stay 16-bit
even when the pakset's water is 32-bit. Open-sea tiles do use the 32-bit images. Open: giving them 32-bit detail is a
new graphics feature (generate them from the 32-bit water, or let the pakset author them) and needs a design decision.

### A7. Night pictures cost memory

An object with a night picture keeps a second full-size 32-bit picture: about **75–93 %** more 32-bit image memory in
our test sets (r12337 measurement, not measured again). By design. **testing-2 itself adds no measurable memory:**
peak working set on Windows 563.4 MB against testing-1's 563.3 MB (pak128.german with its 1950 save, n = 3), peak
memory on Linux 463 MB against 463 MB.

### A8. The pak syntax is a prototype

`night_images=1`, `X.night.png` and the player-colour images are a syntax under review, not a final pak format. Build
test content only with the makeobj of this release (unchanged since testing-1: it writes the same bytes from the test
kit). A night picture that is shifted against the day picture is only detected where the object becomes transparent
at night. After a fatal makeobj error, a partial output file can remain (the exit code is non-zero).

### A9. Builds and platforms

- XR32 is built only with CMake for SDL2 and SDL3. The GDI backend and the plain Makefile build are 16-bit.
- x86_64 only: Windows 8 or newer (official r12361 needs Media Foundation); Linux with glibc 2.38 or newer. The Linux
  SDL2 package uses the distribution's SDL2; the Linux SDL3 package carries SDL3 3.4.12 and loads X11, Wayland and the
  sound systems at run time.
- **Where Linux was tested:** Debian 13 under WSL 2 on Windows 11. The automated tests and the picture checks ran with
  SDL's dummy video driver. The SDL3 package was also run in a **real graphical session, WSLg** (Weston compositor with
  XWayland, one 3440×1440 display at scale 1.0): SDL3 picks X11 by itself, Wayland works when selected, fullscreen and
  back, a window resize, the mouse wheel through X11 (one zoom step per notch; the first notch after activating the
  window is lost, with the SDL2 package too) and a clean exit on every video driver. **WSLg is not a native Linux
  desktop**, and these were not tested: a native X11 or Wayland desktop, HiDPI with a scale above 1, the mouse wheel
  under Wayland, more than one display, GPU drivers other than WSLg's.
- Not tested: macOS, Android, ARM.

### A10. A zoom change costs about 1 ms more (new in testing-2)

The fix for A1/A2 makes the 32-bit scaler sample exactly the grid of the 16-bit one. The first frame after each zoom
change therefore takes longer: +8.7 ms over a walk of 9 zoom steps (+9.0 %, about 1 ms per step, longer in all 7 of 7
paired runs; Frank's pak64.german, Linux). It is paid once per zoom step, because zoomed images are cached: frames
without a zoom change, loading and memory show no measurable difference.

### N2. Identical 16-bit images are merged only within one pak file

The game merges byte-identical 16-bit images only when they are in the same pak file. This is behaviour of the
ordinary 16-bit image reader, not of XR32, and only costs memory; its cause was not established. Open.

### N3. A double-size (MRES) split of a shared image may lose its 32-bit data

When MRES has to split an image that two objects share (both want different double-size art), the copy it makes has no
32-bit data. Found by reading the code; not reproduced (it needs an MRES test pak with exactly that sharing). Open.

### N4. Memory released only at exit

Three pieces of 32-bit renderer memory are not freed before the game exits (an unused release function, a list kept on
an early return, the zoom data of the image table on a path that runs once per game). None of them grows while the
game runs, and the sanitizer runs show no leak through the 32-bit code. Open, no visible effect.

## C. Official trunk r12377 itself

Unchanged from testing-1 (same trunk): B1–B7 of `docs/KNOWN-ISSUES-r12377.md` — founding a city next to a private-way
sign crashes (r12339), empty scenario text files (r12344), the chat's public tab (r12344), music volume after
switching it off and on (r12362), zoomable toolbar icons after a map-zoom round trip (r12368; with `SIMUTRANS_XR32=1`
it does not happen), sanitizer misalignment reports (r12367), and the `old32` link typo (r12362, worked around for
the Windows executables with `patches/r12377/upstream-build-fix/`, not part of XR32). They were not measured again.
