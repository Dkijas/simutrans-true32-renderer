# Known issues — XR32 DAY+NIGHT test build, trunk r12377 (testing-1)

Part A lists the issues of this test build. All of them were already in the r12337 test build: the XR32 code they
come from did not change. Part B lists defects of official trunk r12377 itself. They affect both programs of every
package, they are not caused by XR32, and they are not fixed here.

Each item says whether it was measured again on this build or carried over unchanged from r12337.

## A. This test build

### A1. A 32-bit image can be a few pixels smaller than the 16-bit one at some zoom levels

The 32-bit (XR32) scaler sizes an image to `floor(size × zoom)`. The 16-bit scaler first pads the image to a multiple
of the zoom's denominator, so it can come out larger. Measured on toolbar icons of 31, 33 and 40 px:

| Zoom | Difference |
| --- | --- |
| 3/4, 3/2 and 4/3 | the 32-bit image is 1–3 px smaller |
| 9/8, 5/4, 11/8 and 7/4 (denominator 8) | up to 10 px, and there it is the 16-bit image that is larger than its toolbar cell |

The 32-bit image always fills its cell exactly.

**Measured again:** since r12368 the game fits every toolbar icon once, when the toolbars are built. For Frank's
pak64.german at theme-large, every fitted 32-bit icon has the size of its 16-bit version except one, which is this
rounding case: 277 of 278 on Windows, 280 of 281 on Linux (the total differs because of A3).

### A2. One catenary wire column differs from the 16-bit renderer away from 100 %

pak128.german's `catenary_120`, north-east wire image, has a wire column 1 pixel wide. Away from 100 % zoom the 32-bit
and the 16-bit scalers keep different rows of that column: at 9/8–11/8 the 32-bit image drops its upper 17–21 rows,
and when zooming out the 16-bit image drops more. Carried over.

### A3. Shared images (image identity)

When paks load, the game merges images whose ordinary 16-bit data is byte-identical, **without looking at their 32-bit
data**. Two objects with identical 16-bit images but different 32-bit pictures can therefore end up showing the same
32-bit picture. Seen in testing:
- a test vehicle showed another vehicle's night picture;
- pak128.german's `catenary_tram_90` uses `catenary_160`'s 32-bit mast when both are built with XR32 (their 16-bit
  masts are identical).

**New observation in this build:** which images merge depends on the order in which the system lists the pak files.
Windows and Linux therefore end up with slightly different image sets: with Frank's pak64.german, the game fits 278
toolbar images on Windows and 281 on Linux.

Open; it must be solved before any proposal to Simutrans.

### A4. Coast water tiles have no 32-bit detail

The water tiles on sloped coasts are generated by the game itself from the 16-bit water images, so they stay 16-bit
even when the pakset's water is 32-bit. Open-sea tiles do use the 32-bit images (**measured again** with a recoloured
copy of makie's sea: the marker colour is drawn with XR32 on, and is absent with it off). Carried over.

### A5. 32-bit interface images get dark at night

Toolbar icons and other interface images that come with 32-bit data are darkened at night like the map. 16-bit
interface images keep their day colours, as before.

**Measured again** with Frank's pak64.german and theme-large: with `SIMUTRANS_XR32=1` the toolbar's average brightness
at night is 0.34 of its brightness by day; without it, 0.97.

### A6. At 3/2 the 32-bit picture can depend on the zoom step before it

With `SIMUTRANS_XR32=1`, the map at 3/2 differs by a few pixels (28 px measured on r12337) depending on whether the zoom
step before it was 2/1. Going back through 100 % restores it. The 16-bit renderer has no such effect. Carried over;
not measured again.

### A7. Night pictures cost memory

An object with a night picture keeps a second full-size 32-bit picture: about **75–93 %** more 32-bit image memory,
and zoom changes and night steps rebuild its images about **20–47 %** slower, in our test sets (r12337 measurement,
carried over). The whole-game peak memory of this build is in `NIGHT-PROTOTYPE-MANIFEST.md`.

### A8. The pak syntax is a prototype

`night_images=1`, `X.night.png` and the player-colour images are a syntax under review, not a final pak format:
- build test content only with the makeobj of this release;
- a night picture that is shifted against the day picture is only detected where the object becomes transparent at
  night;
- after a fatal makeobj error, a partial output file can remain (the exit code is non-zero).

**New in this build's makeobj:** it follows official r12375 for the ordinary 16-bit image of a semi-transparent
pixel. A pak with semi-transparent pixels is therefore not byte-identical to the one the r12337 makeobj writes. Its
32-bit data is byte-identical.

### A9. Builds and platforms

- XR32 is built only with CMake for SDL2 and SDL3. The GDI backend and the plain Makefile build are 16-bit.
- This release is x86_64 only:
  - Windows 8 or newer, SDL2 and SDL3. Official r12361 made Media Foundation a requirement.
  - Linux with glibc 2.38 or newer, SDL2 and SDL3. The Linux SDL2 package uses the distribution's SDL2. The Linux
    SDL3 package carries SDL3 3.4.12 and loads X11, Wayland and the sound systems at run time.
- The Linux packages were tested with SDL's dummy video driver, not in a real X11 or Wayland desktop session.
- Not tested: macOS, Android, ARM.
- The port of r12342 to the 32-bit renderer (a line break in single-line text is drawn as a space) is code-ported and
  covered by the automated tests, but it was not checked on its own on screen.

## Fixed in this build

- **Authored double-size (MRES) icons on Linux.** MRES found the object it belongs to by name alone. In Frank's
  pak64.german the menu and the mouse cursor are both called `GeneralTools`. When the system listed the cursor's pak
  last, as native Linux file systems do, the double-size art was paired with the cursor and the toolbar showed the
  enlarged normal icon. MRES now identifies the object by its node type and its name. Measured on a Linux file system:
  this build uses the 2x art, the r12337 test build does not. On NTFS both do.
- **Double-size icons after zooming the map.** With XR32 on, a toolbar icon with authored 2x art showed the enlarged
  normal picture after the map was zoomed in and out, because the 2x art followed the map zoom instead of the icon's
  own fit step. Now it follows the fit step. Measured: toolbar unchanged after the round trip, 2x art used at every
  step; the r12337 test build changes by 6,400 px and drops the 2x art.
